# Модуль «Мастер-данные» (Bride, этап 2)

Справочная основа системы: что сдаём и продаём (модели, экземпляры, комплекты),
кому (клиенты), у кого берём (контрагенты) и на что тратим (счета). Реализован
по ТЗ «Bride — ТЗ: модуль „Мастер-данные“» от 03.10.2026: разделы 1–9 полностью,
открытые вопросы раздела 10 закрыты настраиваемыми значениями по умолчанию (см. ниже).

Интерфейс: **`/md`**. REST API: **`/api/md/…`**. Документация API (OpenAPI/Swagger): **`/api/md/docs/`**.

---

## Как устроено (ТЗ §4.1)

| Что | Где |
|---|---|
| Системные справочники — Django-модели с явными полями и `extra` (JSONB) для доп. полей | `models.py` |
| Описание системных справочников (подписи, типы, группы вкладок, фильтры, поиск) | `registry.py` |
| Пользовательские справочники: `Directory` / `DirectoryField` / `DirectoryRecord` | `models.py` |
| Единый движок: поиск, фильтры, сохранение с журналом, архив, удаление | `backends.py` |
| Бизнес-правила (МД-20, §4.3–4.7) | `api/serializers.py` (миксины по справочникам) |
| Права «роль × справочник × действие» + скрытые/read-only поля (§6) | `api/context.py`, `seed.py` (`default_policy`) |
| Начальное наполнение при регистрации организации (МД-4) | `seed.py`, `signals.py` |
| Маски артикулов, бирки, коды комплектов | `articles.py` |
| Импорт (МД-25…35), шаблоны XLSX | `importer.py`, `tasks.py` |
| Фото: превью, подписанные ссылки, ZIP | `photos.py` |
| PDF-ярлыки 58×40 мм с QR | `labels.py` (шрифт DejaVu в `fonts/`) |
| Шифрование ИИН и номера документа | `crypto.py` |
| История изменений и журнал структуры | `audit.py` |
| Интерфейс | `templates/masterdata/app.html`, `assets/md-app.js`, `assets/md.css` |

Каждая запись содержит `id` (UUID), `organization`, `code`, `is_active` (архив),
`created_by/at`, `updated_by/at`. Записи, на которые есть ссылки, физически не удаляются:
«Удалить» переводит их в архив (МД-21).

**Организации и роли.** В модуле авторизации их не было — добавлены туда же (`accounts`):
`Organization` (настройки разделов) и `Membership` (роль: владелец, администратор,
продавец, бухгалтер). Данные организаций изолированы: чужие записи не видны ни в списках,
ни по прямому id, ни в поиске, ни как значения ссылок (проверено автотестами).

## Запуск

```bash
pip install -r requirements.txt
python manage.py migrate
# пользователь регистрируется на /register (или createsuperuser), затем:
python manage.py md_create_org "Bridal Bliss" owner@mail.kz          # организация + владелец
python manage.py md_create_org "Bridal Bliss" seller@mail.kz --role seller
```

Пользователь без организации при входе на `/md` может сам создать организацию (станет владельцем).
Участников и роли владелец/администратор назначают в интерфейсе: «Организация и права».

В Docker (`docker compose up -d --build`) поднимаются также `redis` и `worker` (Celery) —
для фонового импорта. Без них импорт работает в фоновом потоке процесса.

Команды:

| Команда | Назначение |
|---|---|
| `md_create_org "Название" email [--role …]` | Создать организацию / добавить участника |
| `md_seed` | Досоздать системные справочники и поля для всех организаций (после обновлений) |
| `md_purge_audit --years 3` | Очистить историю старше N лет (не меньше 3 — §8) |

Переменные окружения — в `.env.example` (раздел «Модуль „Мастер-данные“»). Обязательно задайте
**`MD_FIELD_ENCRYPTION_KEY`** и храните его отдельно от бэкапов БД.

## Тесты

```bash
python manage.py test masterdata
```

31 тест, среди них по одному на каждый критерий приёмки §9 (`tests/test_acceptance.py`) и
бизнес-правила (`tests/test_rules.py`). Покрытие кода модуля — **83 %** (требование — от 70 %).
Тесты выполнялись на PostgreSQL 16 с pg_trgm.

Замеры (песочница, PostgreSQL 16, драйвер psycopg без C-ускорения — на сервере будет быстрее):

| Требование §8 | Результат |
|---|---|
| Список до 5 000 записей с фильтрами — до 1 с | 0,3–0,55 с (2 000 экземпляров, 1 000 моделей) |
| Поиск по артикулу/бирке — до 300 мс | 40–90 мс |
| Импорт 1 000 строк — до 30 с | 25 с (каталог «модель + экземпляр», создание 500 моделей и 1 000 экземпляров) |

## Принятые решения по открытым вопросам (§10)

Все решения можно поменять без программиста — через справочники, «Конструктор» или настройки.

| № | Вопрос | Что сделано |
|---|---|---|
| 1 | Размеры и система | Справочник «Размеры» с системой RU/EU/TR/INT; заполнены RU 40–52 |
| 2 | Ростовка | Поле «Длина / рост, см» у экземпляра есть, необязательное |
| 3 | Доп. атрибуты (ткань, силуэт, шлейф) | Не зашиты: добавляются в «Конструкторе» как доп. поля модели |
| 4 | Кодирование артикула | По умолчанию `{PREFIX}-{SEQ:3}` (СВ-117), маску можно задать для каждой категории |
| 5 | Тақия и сәукеле | Подкатегории «Ұзату» (как в §4.6), дерево можно перестроить |
| 6 | Кольцо под платье | Операции «аренда и продажа» — меняется в категории |
| 7 | Что продаётся подружкам и гостям | Новые категории добавляются в справочник «Категории» (префикс, операции) |
| 8 | История цен | Цены хранятся в модели; каждое изменение цены видно во вкладке «История» |
| 9 | Платья как ОС | Задел: ресурс аренд у модели, счётчик аренд у экземпляра, роль у контрагента |
| 10 | Видимость по салонам | Продавец видит товар обоих бутиков (как в §6) |
| 11 | Обязательные фото | Справочник «Типы фото», обязательность не проверяется |
| 12 | Перенос текущего каталога | Импорт экземпляров с колонками «Модель: …» + ZIP с фото (МД-33, МД-34) |

## Ограничения и что дальше

- **Локализация.** Тексты интерфейса собраны в объект `T` в `md-app.js`, но часть подписей
  и все сообщения сервера пока написаны прямо в коде, без gettext. Для казахского языка
  их нужно вынести в файлы локализации — это отдельная задача.
- **S3.** Хранилище подключается переменными `AWS_*` и пакетом `django-storages[s3]`.
  Код рассчитан на это (ссылки с ограниченным сроком), но с настоящим S3 не проверялся.
- **HEIC.** Файлы принимаются всегда. Превью строятся, если установлен `pillow-heif`
  (он есть в `requirements.txt`).
- **Права по салонам** не реализованы (открытый вопрос 10).
- **Согласие на ПДн, ИИН и документ** обязательны «при договоре». Поля и проверки есть,
  а обязательность включит модуль договоров.
